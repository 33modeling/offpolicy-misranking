## Confirmed findings

### F1 - P1: fixed switching trains one extra On-policy update

Location: `scripts/srgc_switch_fixed.py:58-67`.

`SwitchFixedEngine.update()` first calls the base On-policy update and only
then sets `switched_at` when the completed step is greater than `fixed_step`.
For `switch_fixed50`, update 51 still trains On-policy, despite recording the
transition as 50. SR training begins at update 52. The documented contract
and the actual adaptive Switch use SR for update 51 when switching at 50.
The same discrepancy applies at the documented 100, 125 and 200 boundaries.

CPU reproduction used the existing toy backend and forced negative contrasts
at checks 25 and 50 for adaptive Switch:

```text
arm            switched_at    selector at completed update 51
switch_fixed   50             on_policy
switch         50             sr
```

`srgc_rebuttal/tests/test_switch_fixed.py:28-35` currently asserts the late
behavior, so the existing green test is not a boundary correctness check.
This changes a matched-control training trajectory and mislabels its switch
time. It does not establish that the manuscript's archived Switch results
were generated by this newly added control.

Suggested correction: perform the scheduled transition before the update it
governs, preserving the explicitly chosen scoring-cost boundary. Test the
actual trained selector at N, N+1 and N+2 and resume on both sides. Publish
corrected runs separately from any existing fixed-control run.

### F2 - P1: the second dataset bypasses the active cohort resolver

Location: `scripts/run_srgc_rebuttal.py:121-126`.

The primary dataset uses `srgc_pair_inputs.default_plan`, which recognizes an
active Pair-derived cohort or imports its existing initial-policy caches.
The `--with-dataset` path instead hardcodes `mbpp_seeds.json` or
`additional_seeds.json`. Consequently `sh scripts/run_srgc.sh all run` can
serve prepared MBPP inputs while standalone MBPP run/status/results follow
the Pair-derived MBPP cohort. This can spend GPU time on different splits and
caches, and display a different cohort from the one being executed.

CPU reproduction invoked `main()` with `worker --dataset math --with-dataset
mbpp`, mocked external storage/workers, and made the normal resolver choose
Pair plans:

```text
default cohort resolver called for: ['math']
secondary: ['mbpp_seeds.json']
expected secondary: mbpp_pair_seeds.json
```

The problem is conditional on the secondary dataset having a Pair cohort or
reusable Pair source. It is not a claim that every prepared-plan run is wrong.
Use the same dataset resolver for both queues and test active/importable Pair
cohorts as well as the ordinary prepared-plan fallback.

### F3 - P1: MBPP rewards successful process exit without completed tests

Location: `srgc_rebuttal/verifiers.py:48-56`.

Generated code is concatenated before the assertions. A zero interpreter exit
status is accepted as reward 1 even when the candidate exits before any test
runs. Reproduced against the actual verifier, not a mocked subprocess:

```python
from srgc_rebuttal.verifiers import code_reward
assert code_reward({"answer": "assert False"}, "pass") == 0.0
# Observed incorrect reward:
assert code_reward({"answer": "assert False"}, "raise SystemExit(0)") == 1.0
```

This verifier is used by the new MBPP cache, selection/training rewards and
evaluation, including the Qwen adaptation. False positives can alter cached
SR rankings and learning rewards as well as final accuracy. No reviewed
rollout corpus demonstrates how often, if ever, this occurred in real runs.
The historical `src/data.py` / `src/code_sandbox.py` path is a different
implementation; this reproduction does not show that it shares the bug.

Use a trusted test harness that distinguishes normal completion of every
assertion from candidate termination. Cover `SystemExit(0)` and other early
termination paths, ordinary passing/failing code, timeouts, and exceptions.

### F4 - P2: supported fixed-switch arms disappear from result exports

Location: `scripts/srgc_sr_refresh.py:50`, `:337-343`, `:373`.

The CLI and engine accept `switch_fixed<N>`, and V7 explicitly proposes
`switch_fixed200`. Results iterate only the constant list containing fixed100
and fixed125, including in JSON mode. A completed fixed200 endpoint is silently
ignored; it is not reported as invalid or incomplete.

CPU reproduction created a temporary valid plan/prefix/identity fixture and
an endpoint with `arm=switch_fixed200`, `total_updates=275`, matching input and
prefix hashes. The endpoint existed but its key was absent from the JSON row.
No real experiment output was written. Discover supported saved arm names or
take an explicit arm list, applying the existing identity checks to every arm.

### F5 - P2: direction analysis drops the On-policy contrast trajectory

Location: `scripts/srgc_direction_analysis.py:55-60`, with
`scripts/srgc_direction_records.py:65-70`.

The new recording mixin preserves the base engine's `d=None` for On-policy
and fixed-switch controls, where no adaptive decision is made. It does record
the two gradient norms, validation norm and cosines at every refresh. The
analysis reader only copies `d` and the base inner-product fields; it never
reconstructs the diagnostic contrast from those newly recorded quantities.
Consequently the On-policy D column, sign counts and first plot are empty even
for newly instrumented runs with enough information to compute them. This
prevents the advertised direction-versus-magnitude analysis from showing the
full On-policy D trajectory through and beyond an adaptive transition.

Reproduced using `DirectionRecordMixin` + the real Engine with the toy backend,
writing only temporary progress records and reading them with `refresh_rows`:

```text
checkpoint   exported D   D reconstructed from recorded norms/cosines
0            None         +0.0171239806
25           None         -0.0083220307
50           None         +0.0378805449
```

Keep decision records distinct from diagnostics: reconstruct a clearly labeled
diagnostic D/inner products in analysis when the complete finite decomposition
is available, or log separate diagnostic fields. Do not turn On-policy into a
switching arm or fabricate values for older records without these fields.
Tests should assert actual exported D values for On-policy and fixed controls,
not only presence of norm/cosine columns for adaptive Switch.

### Disclosed deployment risk: generated-code isolation

`srgc_rebuttal/DATASETS.md:26-28` explicitly states that the code verifier is
not a security sandbox and requires disposable compute without credentials or
sensitive files. This is a documented deployment limitation, not an undisclosed
new correctness finding. The present audit could not verify that remote nodes
meet this requirement. Python `-I`, resource limits and a temporary working
directory do not restrict absolute-path file access.

A safe reproduction at `srgc_rebuttal/verifiers.py:52-54` read an audit-owned
temporary sentinel outside the verifier's working directory and received
reward 1. No user file, credential, network endpoint or destructive write was
used. Remote deployments must provide the documented isolation externally;
protect experiment outputs as well as credentials. Fixing F3's completion
check does not itself add filesystem isolation.
